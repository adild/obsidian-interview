A **Circuit Breaker** in Spring Boot is a **resilience pattern** used to prevent cascading failures when a service you're calling is **unavailable**, **slow**, or **failing repeatedly**.

Spring Boot supports Circuit Breaker through:
- **Resilience4j** (recommended)
- Hystrix (deprecated)
## 🧠 What Is a Circuit Breaker?
It works like a real electrical circuit breaker:
- When a service **fails repeatedly**, the circuit **opens** (blocks further calls)
- After a timeout, it goes to **half-open** (test if service recovered)
- If successful, it **closes** again (resumes traffic)
## 🔧 Step-by-Step: Implement Circuit Breaker with Resilience4j

### ✅ 1. Add Dependencies
#### `pom.xml`:
```
<dependencies>
    <!-- Resilience4j Circuit Breaker -->
    <dependency>
        <groupId>io.github.resilience4j</groupId>
        <artifactId>resilience4j-spring-boot3</artifactId>
    </dependency>

    <!-- Actuator for monitoring -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>
</dependencies>
```
Actuator dependency is used for checking health for the service. From health we will know which service is up or down.

### ✅ 2. Application Properties
```
resilience4j:
  circuitbreaker:
    # Multiple isntances can be added
    instances:
      myService:  # This is the same name as we gave in @CircuitBreaker 
        registerHealthIndicator: true
        slidingWindowSize: 5
        minimumNumberOfCalls: 5
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 2
      instance2:
	    ....
	    ....
	    ....

# below is actuator configuration
management:
  endpoints:
    web:
      exposure:
        include: resilience4j.circuitbreakers, health, info
```
### ✅ 3. Use Circuit Breaker in Service
```
@Service
public class MyService {

    @CircuitBreaker(name = "myService", fallbackMethod = "fallback")
    public String callRemoteService() {
        // Simulate failure
        if (new Random().nextBoolean()) {
            throw new RuntimeException("Service failed");
        }
        return "Remote service response";
    }

    // Fallback method
    public String fallback(Throwable t) {
        return "Fallback response: Service is temporarily unavailable";
    }
}
```
@CircuitBreaker() annotation is used on the method where we are actually calling other microservice using feign client.
It takes 2 parameters: 
1. name - the service name which we will call
2. fallbackMethod - the method which will get execute if service is down, we need to create the method and provide the implementation.

### ✅ 5. Test It

`GET http://localhost:8080/test`

- Half the time, it will simulate a failure
- After 5 failures (per config), the circuit will **open**
- For 10 seconds, calls go directly to fallback without trying the real method
- After that, it tries again (half-open), and may close if successful

## 🔄 Feign Client Integration

Feign integrates automatically with Resilience4j if you use:
```
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-openfeign</artifactId>
</dependency>
```
Annotate like this:
```
@FeignClient(name = "product-service", fallback = ProductFallback.class)
public interface ProductClient {
    @GetMapping("/products")
    List<String> getProducts();
}

@Component
class ProductFallback implements ProductClient {
    public List<String> getProducts() {
        return List.of("Default Product");
    }
}
```
📌 You can also integrate Resilience4j and Feign explicitly with configuration if needed.

## Retry in circuit breaker
Great! Let's extend the **Resilience4j Circuit Breaker** example to include **retry functionality** as well. Retry automatically attempts failed operations again, based on rules you define (e.g., max attempts, delay between retries).

Simply, when we call any service if it is down then retry will call the service number of times say 3 to check if it actually down or not.

Difference between circuit breaker and retry -
When service is called circuit breaker will return the status.
When service is called retry will internally calls the other service number of times.

### ✅ 2. Configure Retry and Circuit Breaker (`application.yml`)
```
resilience4j:
  circuitbreaker:
    instances:
      myService:
        registerHealthIndicator: true
        slidingWindowSize: 5
        minimumNumberOfCalls: 5
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 2

  retry:
    instances:
      myService:
        max-attempts: 3        # 1 original call + 2 retries
        wait-duration: 2s      # Wait 2 seconds between retries
        retry-exceptions:
          - java.io.IOException
          - java.lang.RuntimeException

management:
  endpoints:
    web:
      exposure:
        include: resilience4j.*, health, info
```

### ✅ 3. Update Service with `@Retry`
```
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.retry.annotation.Retry;
import org.springframework.stereotype.Service;

import java.util.Random;

@Service
public class MyService {

    @CircuitBreaker(name = "myService", fallbackMethod = "fallback")
    @Retry(name = "myService", fallbackMethod = "fallback")
    public String callRemoteService() {
        System.out.println("Calling remote service...");
        if (new Random().nextBoolean()) {
            throw new RuntimeException("Simulated service failure");
        }
        return "Success from remote service";
    }

    public String fallback(Throwable t) {
        return "Fallback: Service unavailable (" + t.getMessage() + ")";
    }
}
```
✅ When `callRemoteService()` fails:
- It will be retried up to 3 times
- If it still fails, the circuit breaker takes over
- If the breaker is open, fallback is used immediately

## Rate Limiter 
Rate limiting in Spring Boot controls the number of requests a client can make to a server within a specified time frame, preventing server overload and ensuring fair usage.

Lets say server is capable of handling only 100 requests in 1 second but lets say 102 requests came then server might get crashed. So to handle this rate limiter is used. 
Benefits:
1. Security: DDOS attack - 100s of requests send in 1 second repeatedly to crash server.
2. Performance

### ✅ 2. Configure Rate Limiter in `application.yml`
```
resilience4j:
  circuitbreaker:
    instances:
      myService:
        registerHealthIndicator: true
        slidingWindowSize: 5
        minimumNumberOfCalls: 5
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 2

  retry:
    instances:
      myService:
        max-attempts: 3        # 1 original call + 2 retries
        wait-duration: 2s      # Wait 2 seconds between retries
        retry-exceptions:
          - java.io.IOException
          - java.lang.RuntimeException

  ratelimiter:
    instances:
      myService:
        limit-for-period: 5           # Allow 5 calls...
        limit-refresh-period: 10s     # ...every 10 seconds
        timeout-duration: 0           # No waiting, reject immediately

management:
  endpoints:
    web:
      exposure:
        include: resilience4j.*, health, info
```

### ✅ 3. Apply `@RateLimiter` Annotation

In your service class:
```
import io.github.resilience4j.ratelimiter.annotation.RateLimiter;
import org.springframework.stereotype.Service;

@Service
public class MyService {

    @RateLimiter(name = "myService", fallbackMethod = "rateLimitFallback")
    public String limitedMethod() {
        return "Processed at " + System.currentTimeMillis();
    }

    public String rateLimitFallback(Throwable t) {
        return "Too many requests. Please try again later.";
    }
}
```
